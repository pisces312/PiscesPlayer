# 节奏游戏：时钟漂移调研与诊断方案

记录一次"音符随歌曲进行越来越不匹配 / 玩到后面下落变快"的排查，以及在真机上定位它所需的诊断埋点设计。

## 1. 症状

用户在新构建（含 osu! 式时钟修复，见 `rhythm-game-integration-plan.md` §6.1.1）上试了两首歌：

- 一首正常；
- 另一首（中文流行曲，本地 mp3，172.874 s）**玩到后面音符下落变快、与歌曲越来越不匹配**。

"下落变快"是关键判据：音符视觉下落速度 = `scrollLength / approachMs`（每毫秒像素），是常量。能让它变快的只有时钟 `now` 走得比真实音频快（over-run），且误差随时间累积。谱面本身产生不了"下落速度变化"这个现象——谱面只决定音符的绝对时间戳。

## 2. PC 侧谱面复现（结论：谱面无渐进漂移）

用 ffmpeg 把该 mp3 解码成 44.1kHz 单声道 PCM（172.874s），跑真实的
`RhythmChartGenerator.analyze → renderMaster → RhythmChartDeriver.derive(EASY)` 全链路：

| 项 | 值 |
|---|---|
| detectedBpm | 170.99 |
| 独立交叉验证（onset 相位集中度）最佳 BPM | **170.5**（与检测一致 → 速度没测错，不是八度错误） |
| master 音符 | 1305（首 87ms / 尾 172739ms） |
| EASY 派生 | 493，间隔**全是 350–351ms**（严格一拍一 note，密度全程恒定） |

**EASY 相对 master 的时间残差，按 10 段分桶：**

```
段          mean残差   maxAbs
0-17s        +2.9      142
17-35s      +16.8      162
35-52s      +21.3      119
52-69s      -16.0      119
69-86s      +10.4      132
86-104s      -2.9      168
104-121s    +17.1      134
121-138s    +11.6      120
138-156s     +9.0      110
156-173s     +8.1      104   ← 结尾反而最紧
```

残差**不随时间增长**（在 ±20ms 间震荡，无单调趋势），结尾段最大偏差(104ms)比开头(142ms)还小。数学上也成立：网格吸附残差恒被 `grid/2` bound 住，不会累积。

**结论：master 与 EASY 派生谱的绝对时间戳在全曲 172 秒内均匀贴合真实 onset，没有任何渐进漂移。"下落变快"不是谱面问题。**

### 2.1 顺带发现（非本次症状，但值得记一笔）

这首歌节拍很弱（相位集中度仅 0.064，onset 大量是 50/100ms 的密集细分），导致 EASY 有
**110/493 (22%) 的 note 距最近真实 onset >60ms，43/493 (8.7%) >90ms（GOOD 窗外）**。
这是"谱面贴合度"问题，全曲均匀分布，与"下落变快"无关。后续若要提升弱节拍歌曲的谱面质量，
可考虑对低集中度歌曲放宽吸附或降低 EASY 密度。

## 3. 为什么焦点回到时钟

谱面已排除，剩下的唯一能产生"渐进 over-run"的是播放时钟：`nowMs()` 相对真实音频位置越走越快。
可能来源（均需真机数据区分，PC 测不了 AudioTimestamp / playbackHeadPosition 行为）：

- 设备无 AudioTimestamp（或 `getTimestamp` 一直返回 false），时钟退化为 head + 墙钟外推；
  DAC 实际速率与标称 44100 有微小偏差（几十~上百 ppm），墙钟外推按标称速率跑，误差逐秒累积。
- head 采样被 timestamp 新鲜度门控长期挡住，导致墙钟自由跑。
- 写入线程被 CPU/GC 饿死造成 underrun，head 停走后又恢复。

## 4. 诊断埋点设计（本次实现）

核心思想（用户提出）：**在音符过线的时刻，比较"谱面给的时间"与"音频实际已播放的长度"**，
两者之差随时间的走势即漂移。

### 4.1 每帧采样

游戏循环每帧已经在读一次 `clock.nowMs()`。让 `RhythmAudioClock` 在同一次读取里顺带记录原始量，
不额外读设备：

| 字段 | 含义 |
|---|---|
| `wallMs` | 自时钟 start 起的墙钟毫秒（`SystemClock.elapsedRealtimeNanos` 差） |
| `songMs` | `nowMs()`，驱动渲染/判定的时钟值 |
| `headMs` | `playbackHeadPosition / sampleRate * 1000`（未经延迟补偿，设备真值之一） |
| `timestampMs` | AudioTimestamp 推出的"当前正被听到"的帧位置（延迟补偿，最可信真值；无则 NaN） |
| `source` | 本帧时钟实际采信了哪个源（TIMESTAMP / HEAD / WALL） |

判据（与设备源是否可信无关）：

- **`songMs − wallMs`**：斜率应恒为 1.0（1ms 墙钟对应 1ms 歌曲）。> 1 即时钟 over-run → 音符下落变快。这是最直接对应用户症状的量。
- **`audioRefMs − wallMs`**（audioRef = timestampMs 优先，否则 headMs）：真实音频相对墙钟的速率，用来区分"时钟跑快"还是"音频本身播快"。
- **`songMs − audioRefMs`**：音符领先真实音乐多少 = 玩法上真正感知的漂移。

为控制导出体积，trace 降采样到约每 100ms 一条（172s → ~1700 条）；note-crossing 事件全量保留。

### 4.2 音符过线事件

每当一个 note 到达判定线（`songMs` 越过 `note.timeMs`），记录
`(noteId, noteTimeMs, songMs, audioRefMs, residual = noteTimeMs − audioRefMs)`。
residual 随 noteTimeMs 的走势若线性增长，即"越到后面越不准"的直接证据。

### 4.3 自动分类

`RhythmDriftAnalyzer`（纯 Kotlin，JVM 可测）对 `songMs − audioRefMs`（或 `songMs − wallMs`）序列
做最小二乘线性回归：

| 分类 | 判据 |
|---|---|
| `STABLE` | 斜率≈0 且残差全程有界（< ~40ms） |
| `PROGRESSIVE_OVER_RUN` | 斜率显著 > 0（时钟比音频快，音符越来越早/下落变快） |
| `PROGRESSIVE_UNDER_RUN` | 斜率显著 < 0（时钟比音频慢，音符越来越晚） |
| `STEP` | 残差在某点发生一次性跳变（underrun 恢复 / seek） |
| `SAWTOOTH` | 有界震荡、无净趋势（设备采样稀疏，帧间外推锯齿） |

报告输出：斜率（ms/s 与 ppm）、末段总残差、最大 |残差|、主导源、note-crossing residual 趋势。

### 4.4 导出与展示

- **游戏界面**：暂停页加"导出诊断日志"入口（一局中途也能导）。
- **结算界面**：加"导出诊断日志"，并把自动分类结果（如"时钟渐进超前 +85ms，快 0.5ms/s"或
  "时钟稳定，无明显漂移"）直接打印在完成界面上。
- 导出实现沿用仓库既有模式：写文件到 `cacheDir` → `FileProvider("${packageName}.provider")`
  → `Intent.ACTION_SEND` chooser（`file_paths.xml` 已暴露 cache 与 files）。
- 记录默认常开（每帧一次小对象写入，开销可忽略），这样结算界面才能给出分类。

## 5. 交付边界

本埋点只负责**观测与归因**，不改时钟算法。拿到真机一局日志、确认 over-run 的量级与来源后，
再决定时钟侧的修法（例如：无 timestamp 时用 head 的相邻差反推真实 DAC 速率来校正外推斜率，
而不是按标称 sampleRate 外推）。

## 6. 真机日志结果与根因（2026-11-03）

真机一局 173 s（应用导出的 `rhythm-drift-*.txt`，同一首歌）的结论，与本文 §2 的谱面分析合起来才完整：

### 6.1 时钟：稳定，不是漂移源

| 量 | 实测 |
|---|---|
| `songMs − wallMs` 斜率 | 999.8 ms/s（p50），p90 1004.7，p99 1008.9 |
| `songMs − timestampMs` | 每 5 s 桶均值都在 +19…+22 ms，min≈0，max≈40 |
| 主导源 | TIMESTAMP（覆盖率 1.00） |
| 分类器判 `STEP` | 假信号：最大跳变 199.85 ms 出现在 `wall=113.9`（开播第一帧的时间戳锚定），不是游戏中的漂移 |

那 0–40 ms 的锯齿是 **AudioTimestamp 的更新粒度/年龄**（`song = 时间戳帧 + 自时间戳以来的墙钟`），
不是时钟抖动。全程没有任何趋势项。**时钟可以排除。**

### 6.2 根因：全局 BPM 估计误差 0.4%，网格循环失配

对同一 mp3 做整曲节拍分量相位回归（8 s 窗、Hann、相位解卷，`conc>0.35` 的 300 个窗口）：

| 量 | 值 |
|---|---|
| 谱面实际使用 | `usedBpm = 171.034`，`beatMs = 350.808`，`offset = 185.77` |
| 音乐真实速度（相位回归） | **170.355 BPM**（细扫复数解调峰 170.32） |
| 每拍误差 | ≈ 1.4 ms（0.40%） |

误差会累积成完整的**锯齿**：谱面网格相位相对音乐从 +124 ms 一路滑到 −149 ms，
回绕到 +169 ms，再滑回来 —— **约 94 秒完成一个循环**，幅度 ±半拍（±175 ms）。实测
"网格相位残差"（音乐节拍分量 vs 谱面格子）在旧参数下从 +63 → +168 → −135 → −64 → +42 → +158 → −148 ms，
在 173 s 内回绕近两次。这正是"一会正确、一会快、一会又正确，不断循环"：网格对齐时准，
滑到半拍就明显错，再滑一整拍又"看起来准了"。

§2 的 decile 表其实已经埋了这个信号（有符号均值 +21 → −16 → +17 来回摆），当时只看了
"不随时间增长"，把**速度误差导致的循环**误判成了"无渐进漂移"。

### 6.3 修复：整曲相位相干细化 BPM

`RhythmChartGenerator.refineTempo()`：在自相关粗估（及其抛物线插值）之后，于 ±1% 内扫描
整曲复数解调幅度 `|Σ novn·w·e^{−iωt}|`，再对峰做抛物线插值。自相关峰宽、只有 ~0.3% 精度；
而相位在整曲上积分，峰宽 ~1/T（3 分钟歌里不到 0.4 BPM 的几分之一）。

同一首歌修复前后（音乐节拍分量 vs 网格的相位残差，8 s 窗）：

| | 残差范围 | sd | 斜率 |
|---|---|---|---|
| 修复前 `171.034` | −173 … +175 ms（整拍回绕） | 103.5 ms | — |
| 修复后 `170.299` | −84 … +76 ms（无回绕） | 36.7 ms | −0.32 ms/s（全程 −55 ms） |

残余 ±70 ms 的缓慢起伏是这首歌自身 ±0.05% 的局部速度摆动，单个全局 BPM 无法消除；
若日后仍觉得结尾略偏，可考虑多 timing point（`RhythmChart.timing` 本就是列表）。

### 6.4 注意

- **已生成的旧谱面不会自动变好**：BPM 是生成时写进 `timing` 的，必须重新生成谱面才生效。
- 这是一次性生成期修复，不影响运行时时钟；§5 的边界仍成立。
- 回归测试：`RhythmChartGeneratorTest.usedTempoMatchesTheLoopPeriod`（60 s、120 BPM、±0.05）。
  120 BPM 而非更高速度：合成鼓点在 137.4 BPM 上会落入既有的八度歧义（锁到 ~68），
  那是 `chooseOctave` 的问题，与本次细化无关。
