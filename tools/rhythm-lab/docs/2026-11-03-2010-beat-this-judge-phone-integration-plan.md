# Beat This! 裁判式调参上手机：集成方案（2026-11-03 20:10）

目标：把 PC lab 的"生成 → 对裁判扫参 → 选最优"闭环搬进手机生成流程。
前置事实（均已实测）：Beat This! final0 = 20.25M 参数 / 81 MB fp32 / PC CPU 40× 实时；
int8 后约 20 MB。自洽调参已实测否定（`2026-11-03-pc-lab-alignment-under-20ms.md`），
所以裁判必须是 Beat This! 本身。

## 角色定位（重要）

- **细网格仍由 DSP tracker 的分段拟合产生**：Beat This! 有 50 fps 的 10–20 ms 噪声底，
  直接拿它的拍点当网格会继承抖动。
- Beat This! 只做两件事：**段级相位/计数裁决** + **候选扫描的裁判**。
- 预期收益是尾部（坏段落对齐、开头锁定段选参），不是中位数（5–12 ms 已贴噪声底）。

## 阶段一：参考拍点提供者（不进生成路径）

1. **模型准备**：torch → ONNX 导出 final0（含完整预处理图或预处理移植）；
   PC 上 onnxruntime 与 PyTorch 逐位对照（同一 wav，beat logits max |diff| 目标 < 1e-4）；
   动态 int8 量化压到 ~20 MB。
2. **运行时选型**：首选 ONNX Runtime Mobile（arm64 单 ABI，XNNPACK 线程），
   备选 MNN（更快但 JNI/构建成本高）。若 ORT 实测耗时 > 3 min/首 再考虑换。
3. **预处理对齐**：复刻 Beat This! 的重采样/mel/STFT 前端，逐位对照 Python 输出；
   音频直接复用 app 已有的 44.1 kHz mono PCM。
4. **模型交付**：待拍板——APK 内置（+20 MB，简单）vs 首次按需下载
   （release asset，包体不变，多一段下载/校验逻辑）。
5. **输出**：参考拍点列表（ms）落盘到 rhythm 数据目录；诊断导出可附带它供 PC 对照。
6. **验收**：2–3 首歌，手机拍点 vs PC `reference/*.txt` 逐点差 < 1 ms；
   实测耗时/内存；飞行模式下可用。

## 阶段二：裁判式调参 + 相位裁决（进生成路径）

1. **候选扫描**：tightness {200…1200} × 拟合窗 {6,10,16}（可加全局相位奇偶），
   每候选 1–3 s；判据 = `tune_tracker.py` 同款排名（div4 的 max → p99 → p95）。
2. **段级相位裁决**：8 拍一段，把参考拍投影到拍圆算 bias = Σcos(2πφ)/N；
   bias < −0.1 翻该段半拍。**段内参考拍 < 4 颗跳过**（防空窗/间奏伪影，
   有生之恋 outro 的 5.76 s 空窗就是这类）。
3. **兜底**：模型缺失/失败 → 保持现有默认参数（今天的整条行为不变）；
   手动 BPM override → 5% 拍长守卫语义不变（扫描种子仍用 override）。
4. **记录**：选中参数 + 参考拍点写进 chart diagnostics（导出可复盘）。
5. **测试**：Kotlin 单测（合成 wav 的候选选择/相位翻转断言）+ 黄金夹具不回归；
   落地后用真实管线对 6 首验证曲重跑 `judge_optimize` 同口径验收。

## 成本与预期

- APK +~20 MB（int8）；每首生成 +1–2 min（Beat This! 30–90 s + 扫描 30–90 s，
  后台跑带进度）。
- 预期：坏段落按计数对齐、开头段选中更优参数（基线曲同类场景 max 119→61）；
  "全线 <20 ms"仍受 50 fps 噪声底限制，不做此承诺。

## 待拍板

1. 模型交付：APK 内置 vs 按需下载。
2. 相位裁决的朝向：Beat This! 计数相位（本方案默认）vs 听感/onset 相位——
   两处滑动段的听感裁决还没做，若听感支持 tracker 现状，此步可省。
