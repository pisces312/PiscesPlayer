# PC 实验：把网格谱面与原曲的误差压到 20 ms 内（2026-11-03）

针对真机日志里"分段后仍严重跑偏"的问题，在 PC 上把基线歌曲
`E:/迎着风向前冲-姜月初.mp3` 作为回归基准，先离线验证出一套能稳定达标的
谱面生成配方。本轮**只改 lab（Python），未改 app 代码**。

## 结论

误差的主要来源不是时钟，也不是"分段不够细"，而是**生成侧的前端与跟拍**：

1. 8 个频带的 novelty 分辨率太低，DP 跟拍在中后段整拍漂移
   （相对 Beat This! 参考：中位 20.3 ms、p95 327 ms）；
2. 旧的 comb 相位把 30.35 帧的周期四舍五入成 30 帧再折进残差表，
   相位本身就算错了（导出 offset 139 ms，而细扫相位约 328 ms，且逐窗口漂移）；
3. 曲尾混响里的"拍"被当成真拍，最后一段网格被拖晚。

改成 **64 频带 novelty + 半速 DP 跟拍 + RMS 尾部门控 + 加权分段线性拟合** 后，
三个难度（div 1/2/4）的网格线全部落在 20 ms 内。

## 指标口径

- 谱面难度 `d` 的网格间距是 `beatMs / d`，与参考拍的 `d × 2` 等分网格逐线比较
  （本曲谱面拍 = 八分音符，参考拍 = 四分音符，ratio = 2）。
- 评估区间固定为 **2000 ms … 最后一颗参考拍（171361 ms）**，
  不延伸到曲尾：171.4 s 之后只剩混响，外推网格会让 max 失去意义。
- PASS 判据：每个难度的 `max |error| ≤ 20 ms`。

## Kotlin 落地方案（已实施，见下节实测）

目标：让生产管线自己产出的 `master.timing` 就是这套分段网格，GRID 派生直接使用它，
不再依赖 `RhythmTimingRefiner`。**onset 检测保持现有 8 频带不动**，64 频带只服务节拍跟踪，
这样母谱音符集合与黄金夹具都不变，改动只影响网格相位与拍长。

1. 新文件 `RhythmBeatTracker.kt`（`internal object`，纯 Kotlin/JVM，无 Android 依赖）
   - `novelty64()`：沿用现有 N_FFT=2048 / HOP=512 / 对数频带边 / 32 帧 running-max /
     `log1p` / 半波整流 / p95 归一；44.1 kHz 下实际得到 52 个不同频带。
   - `beatTrack()`：novelty 先按 std 归一；`startBpm = usedBpm / 2`（谱面拍是音乐拍的一半）；
     `tau ∈ [round(period/2), round(2*period)]`；转移罚 `600 · ln(tau/period)²`；
     回溯从末尾 `2*period` 帧内累计值最大处开始；在 ±2 帧内找局部峰并做抛物线细化。
   - `trimSilentTail()`：拍点处 100 ms 局部 RMS 低于全曲 100 ms RMS 中位数的 0.25 时，
     只从尾部丢弃（前奏安静不受影响）。
   - `fitTiming()`：每颗音乐拍一个锚点；±10 拍窗口；权重
     `clip(1 - |i-a| / 11, 1e-3)³`；最多 4 轮残差裁剪，阈值 `max(45 ms, 3×中位残差)`；
     `beatMs = slope / 2`；锚点取整到毫秒落盘；`extraOffsetMs` 整体平移所有锚点。
   - 守卫：少于 2 颗拍，或拟合中位拍长与 `60000 / usedBpm` 偏差超过 5% 时，
     退回单锚点方案（拍长沿用用户/检测 BPM），避免把错拍率写进谱面。
2. `RhythmChartGenerator.analyze()`（`RhythmChartGenerator.kt:99`）
   - tempo 估计之后运行 tracker；`DspAnalysis` 增加 `timing: List<RhythmTimingPoint>`；
   - 删除 comb 相位段（当前 264–286 行）；`beatOffsetMs` 改为首个锚点，仅保留诊断含义；
   - `renderMaster()` 写完整 timing；`render()` 改用同一份 timing 做吸附，
     维持"直接渲染 == 派生"的既有约束。
3. `RhythmRepository.gridTimingFor()`（`RhythmRepository.kt:232`）
   - `master.timing.size > 1` 时直接返回；否则退回 `RhythmTimingRefiner`，只服务旧母谱。
     重新生成的母谱自动走新网格；旧母谱重生成一次即可受益。
4. 测试
   - 新增 `RhythmBeatTrackerTest`：恒速合成鼓（锚点间距 ≈ 期望拍长）、淡出尾部被丢弃、
     BPM 守卫回退。
   - 更新 `RhythmChartGeneratorTest` 中"单段 timing"的三处断言。
   - 黄金夹具（8 频带 onset 未动）预期仍通过；若时移超过 ±15 ms，先查吸附相位，
     不擅自重新生成夹具。
5. 验收
   - PC：`run_lab.py export`（真实 Kotlin 管线）→ `analyze`，要求 div 1/2/4 的
     `max ≤ 20 ms` 且 100% 覆盖；
   - `:app:testDebugUnitTest` 与 `:app:assembleRelease`；
   - 装 release APK，对 `迎着风向前冲` 重新生成母谱 + 两种派生，试玩确认。

### 一个真实的边界 bug（已修）

锚点取整成毫秒而 `beatMs` 保留小数，段内最后一条网格线会四舍五入到下个锚点 ±1 ms，
同一拍被拆成两个相差 1 ms 的格子（基线曲 19 个段边界里 10 个如此，EASY 谱多出 8 个音符）。
`snapTime` 现在把"段内最后一条格线"直接吸附到下一个锚点，边界拍唯一。

### 黄金夹具的相位冲突（待用户裁决）

`RhythmChartGeneratorGoldenTest` 的难度谱对比现在只剩**相位**不通过（计数已通过）：
match 55–77%（15 ms 容差、要求 95%）。三方网格相位实测（dsp-beats-120bpm 合成曲，
真实拍点在 0+k·500 ms）：

| 网格 | 相位偏差 | 拍长 | 20 s 末偏差 |
|---|---|---|---|
| 真实（合成拍点） | 0 | 500.000 | — |
| 新 tracker | +5.5 ms | 500.02 | ~10 ms |
| 夹具 oracle（Python 原型） | +26.5 ms | 499.72 | ~25 ms |

夹具的期望值来自原型自己的 offset 估计，比 tracker 差约 21 ms；tracker 是对的
（对 Beat This! 18.9 ms 也印证）。**未擅自重新生成夹具**，选项：
A. 用 tracker 网格重生成难度谱期望值（改 `gen_dsp_fixture.py`）；B. 难度谱对比先对齐相位再比 15 ms；
C. 容差放宽到 ~40 ms。母谱（raw onset）对比不受影响，仍然 15 ms 全过。

1. **开头锁定段**：就让岁月 2–6 s 误差 +243 → +115 递减收敛（参考首拍 672 ms 之前的

2. **弱打击段的半拍相位滑动**：有生之恋 20–40 s、玉盘 Live 100–140 s 的 tracked beats
   本身落在参考拍点之间（±250 ms ≈ 半拍），**不是拟合问题**。谁对谁错需听感裁决：
   DP 跟到了反拍，或 Beat This! 在该段选了相反相位。
3. **参考自身的伪影**：有生之恋 outro 参考 145.99–151.76 s 无拍点（5.76 s 空窗），
   指标把该段网格线记成 ±2.7 s 误差（max 2705 全部来自这里）；另有 104 ms 双拍毛刺。
4. **真实小漂移**：阳光灿烂 10–16 s 约 52 ms（该段参考拍间隔 473–479 vs 中位 468，

附加发现：检测器的八度选择不统一（chartBpm 3 首 = 2×乐拍、2 首 = 1×、阳光灿烂 = 0.5×），
只影响网格密度/手感，不影响相位；指标按 `ratio` 自适应，不受影响。

## 自洽最优验证：手机端参数优化可行吗（2026-11-03，结论：否定）

问题：手机上生成谱面后想做逐歌参数优化，但手机上没有 Beat This! 当裁判，
目标函数只能"自洽"（网格与自身 onset 的吻合度）。本实验在 6 首歌上验证自洽评分
能否替代外部裁判；工具 `experiments/selfscore.py`，候选 = tightness {200…1200} ×
拟合窗 {6,10,16}，逐候选跑真实 tracker，以 Beat This! 为真值裁判对照排名。

### E1 参数选择：信号太弱

- 自洽分在候选间的摆幅只有 0.001–0.07（yupan-live 的 15 个候选同分到小数点后 3 位），
  与裁判排名的 Spearman 相关 −0.59…+0.51，方向不稳。
- 候选间的真值差异本身也很小（div2 中位数只动 1–6 ms），默认参数始终贴着最优：
  "每歌参数没调好"不成立——**参数空间里本来就没有多少可捡**。
- 唯一看得见的增益：就让岁月的开头锁定段，ref-best（tight 1200 / win 16）把 div2 max
  119 → 60.7 ms，但自洽分选不中它（自选 124.3）。想吃这个增益得用别的信号。

### E2 相位投票：坏段落无证据，有证据时也不站参考那边

- 判别必须在 div-1 拍圆上做：div-2 网格平移半拍等于网格自身，第一版实验因此
  恒等无效（已修，教训留档）。
- 8 拍分段相位偏置 C = Σw·cos(2πφ)/Σw（φ 为 onset 在当前拍内的位置）：
  已知滑动段（有生之恋 20–40 s、玉盘 Live 100–140 s）C ≈ 0 ~ +0.11，
  **onset 证据不判相位**，弱支持 tracker 当前相位。
- 全部约 130 段仅 1 段触发翻转（雨落哗声 14.9 s，C=−0.14），翻转后参考误差
  42 → 228 ms——假阳性。阈值再收紧就一票不发。
- 两处"半拍滑动"在自洽意义下**不可判**：本质是"跟 onset 相位"与"跟 Beat This!
  计数相位"的约定之争，要听感裁决。

### 结论

- **手机端逐歌参数优化：不做**（自洽评分无分辨率，实测否定）。
- 想要更强的相位/计数判据只有两条路：把 Beat This!（20.25M 参数 / 81 MB /
  PC CPU 4.5 s 跑完 3 分钟曲 ≈ 40× 实时，int8 后约 20 MB）搬上手机当先验或裁判；
  或接受"音符跟 onset"的语义（对游戏未必是错）。
- 真实改进点是结构性的（开头锁定收敛），固定成本、全曲库受益，与逐歌调参无关。

## 裁判式调参模拟：手机端优化机制的收益上界（2026-11-03，`experiments/judge_optimize.py`）

手机集成方案见 `2026-11-03-2010-beat-this-judge-phone-integration-plan.md`。本实验模拟
"Beat This! 在手机上当裁判"的完整机制：每曲扫 tightness × 拟合窗 15 个候选、按
`tune_tracker` 的 (div4 max→p99→p95) 排名选优，再做裁判版 8 拍段级相位翻转（bias<−0.1
翻半拍，段内参考拍 <4 颗跳过）。选择与投票用的就是评估裁判，故数字是**收益上界**。

| 曲目 | 默认 div4 ≤20%/max | 优化后 | 主要变化 |
|---|---|---|---|
| 基线 | 100% / 19.6 | 100% / 19.6 | 已到顶 |
| 就让岁月 | 88.1% / 61.7 | **97.2% / 60.7** | 选中 1200/16，开头锁定段大幅收敛（div1 max 243→60.7） |
| 有生之恋 | 75.6% / 713.5 | 70.4% / 705.6 | **变差**：4 段翻转把 div1 拉向参考拍标记，div2/4 反而掉 |
| 阳光灿烂 | 92.7% / 51.8 | 93.7% / 41.0 | 选中 400/16，小幅 |
| 玉盘 Live | 91.7% / 35.0 | 91.6% / 34.0 | 2 段翻转修好 div1（p95 241→23.3） |
| 雨落哗声 | 98.9% / 100.7 | 99.0% / 88.9 | 选中 200/16，小幅 |

div4 超 20 ms 的线合计 **662 → 585（−12%）**。两条硬教训：

1. **翻转会误伤"裁判数错拍"的段**：有生之恋 20–40 s 翻转后 div1 微升、div2/4 下降
   ——该段 div2 网格本来就贴着参考的细分网格，是 Beat This! 把拍标记打在反拍上。
   这是"滑动段可能是裁判的约定问题"的定量证据。手机实现里投票应改为
   **逐段试两个相位取总误差小者**（裁判在手，可直接 argmin），而不是 bias 启发式。
2. **排名判据会被裁判伪影劫持**：有生之恋的 max 全程被 5.76 s 空窗支配，按 max 选参
   捡了芝麻（713→705）丢了覆盖率（75.6→70.5）。裁判带伪影时应按
   **≤20% 覆盖率优先**、max 只作次级判据。

### 开头锁定段：成因与结构修复（2026-11-03 补，已实施）

以就让岁月为例，tracked beats 对参考拍的逐拍误差：

```
tracked 拍时刻      误差        参考拍点: 672 / 1688 / 2687 / 3698 / 4693 ms
   52.3 ms     −619.6 ms        ← 参考第一拍之前的纯外推区
 1024.9 ms     +353.0 ms
 1966.1 ms     +277.9 ms
 2896.7 ms     +209.9 ms
 3847.5 ms     +149.7 ms        ← 之后收敛到 ±20 ms
```

tracked 拍间隔 930–970 ms vs 参考 ~1000 ms：**前几拍 DP 锁到了快 5–7% 的错速度**
（引入段打击稀疏、有 pickup，证据不足以定速）。div1 网格线误差 +243 → +115 递减，
就是拟合窗口逐渐装进好拍后的"追赶"过程。

**修法（`experiments/intro_fix.py` 三方对比后定稿）**：

1. **锁定点检测**：全曲拍间隔的中位数（= 全曲速度，坏开头只占 ~3%、偏置 <0.2%）
   做基准；从左扫，第一颗满足"后 8 拍间隔全部在 ±3% 内"的拍是锁定点 L。干净歌曲
   L=0、完全无操作（6 首里 baseline/yangguang/yupan-live 无操作，yuluosheng L=1
   无变化）。
2. **开头回填**：L 之前的锚点按 **全曲中位拍长** 从 L 处拟合值向后外推。实测
   "全曲速度"优于"L 处局部拟合线斜率"（div2 max 114.8 vs 141.5）——局部拟合在
   锁定边界仍被坏拍轻微拖偏，全曲中位更稳。
3. 兜底：找不到稳定段则不修。

**实测（就让岁月，真实 Kotlin 管线复测与原型逐位一致）**：

| | div1 med/p95/max | ≤20 ms |
|---|---|---|
| 修复前 | 7.6 / 78.3 / 243.6 | 85.5% |
| 修复后 | 7.3 / 48.3 / **114.8** | 86.4% |

剩余 max 114.8 **已不在开头**（8 s 前 >20 ms 的线从 ~50 条降到 11 条且全部 <93 ms），
最差点转移到 66–68 s——那是参考拍自身的八度翻转段，与本修复无关。基线曲 100% 保持不变。

## 生产化前必须知道的风险

- 达标区在 DP tightness 上很窄：400 会退化到 max ~42 ms，600–1000 才稳定；
  已用同参数过 5 首不同曲风（见上节），未再逐曲扫参。上节四类失败里，
  开头锁定段与弱打击段半拍滑动是 tracker 侧可改进项，参考伪影不可修。
- Beat This! 是 50 fps 模型，即使做了亚帧插值，参考自身仍有约 10–20 ms 噪声；
  p95 ≈ 11.7 ms、max ≈ 19.6 ms 已接近该参考的分辨率下限。
- 新 timing 只在重新生成母谱后生效；旧母谱（单段 timing）派生网格仍走 `RhythmTimingRefiner`。
